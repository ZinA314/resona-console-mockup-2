## 목표

콘솔 창이 가려지거나 최소화돼도 출력 창이 계속 돌게 한다.

## 배경

3단계 검증 중에 실제로 겪은 문제다. 분석과 송출이 콘솔의 `requestAnimationFrame` 에 얹혀 있어서, 콘솔 창을 최소화하거나 다른 탭으로 넘어가면 출력 창도 함께 멈춘다. 브라우저가 보이지 않는 창의 rAF 를 멈추기 때문이다.

두 디스플레이에 창을 나란히 띄우는 정상 배치에서는 둘 다 `visible` 이라 문제가 없다. 그러나 공연 중에 오퍼레이터가 파일 탐색기나 다른 프로그램을 잠깐 앞으로 부르는 일은 반드시 일어난다. 그 순간 무대가 정지한다.

`CLAUDE.md` 에 적은 원칙에 걸린다.

> 공연 중에 쓰는 도구입니다. 한 부분이 실패해도 화면은 계속 돌아야 합니다.

## 왜 지금 하는가

6단계-A 에서 무대 씬을 얹으면 출력 창이 이 프로젝트의 주인공이 된다. 그 전에 토대를 고쳐 두는 편이 낫다. 무대 씬을 올린 뒤에 손대면 멈춘 원인이 셰이더인지 창 상태인지 구분하기 어렵다.

## 워크렛은 시계로만 씁니다

**특징 추출을 워크렛으로 옮기지 않습니다.** 그러면 `AnalyserNode` 를 버리고 FFT 를 직접 구현해야 하는데, 창 함수와 스케일이 미묘하게 달라져 2단계에서 어렵게 맞춘 값들이 전부 흔들립니다. 온셋 임계값 `중앙값 × 1.5 + 0.022`, BPM 빗살 가중치, 밴드 정규화 배율이 모두 `AnalyserNode` 의 출력 스케일에 맞춰 정해진 값입니다. 아래 완료 기준의 "리드아웃 수치가 예전과 같다"와 정면으로 부딪힙니다.

**워크렛은 창 상태와 무관하게 도는 시계 역할만 합니다.**

```
[오디오 스레드]  워크렛 = 약 60Hz 시계
       │ port.postMessage({ dt })      창이 최소화돼도 계속 간다
       ▼
[메인 스레드]   analyze()  ← AnalyserNode.getByteFrequencyData 그대로
                onset · tempo · stems · 상태 · 분위기 · 팔레트
       │ BroadcastChannel
       ▼
[출력 창]      자기 rAF 로 그린다
```

메인 스레드가 백그라운드에서도 이 메시지를 처리합니다. 브라우저의 백그라운드 절전은 타이머(`setTimeout` 계열)와 `requestAnimationFrame` 에 걸리고, 메시지 포트 콜백은 대상이 아닙니다. **소리를 내고 있는 탭은 크롬의 탭 얼리기 대상에서도 제외됩니다.**

워크렛의 `process()` 는 128 샘플마다 불리므로 44.1kHz 에서 약 344Hz 입니다. 여섯 번에 한 번 보내면 약 57Hz 가 됩니다. **정확히 60Hz 가 아니므로 `dt` 를 함께 실어 보내고, 받는 쪽은 그 값을 씁니다.**

## 작업

- [ ] **`lib/audio/analyser.worklet.js`** 를 시계로만 만든다. 여섯 번째 `process()` 마다 `dt` 와 함께 `postMessage`
  - 확장자가 `.js` 인 것은 의도한 것이다. 워크렛은 브라우저가 직접 파싱하는 별도 모듈이라 번들러가 `.ts` 를 그대로 내보내면 로드에 실패한다 (실측: `AbortError`)
  - `new URL('./analyser.worklet.js', import.meta.url)` 로 잡는다. 번들러가 해시 파일명을 붙여 별도 자산으로 내보내므로 캐시 문제가 없다
  - 틱 주기는 표본율에 따라 다르다 (48kHz 에서 62.5Hz, 44.1kHz 에서 약 57Hz). **`dt` 를 실어 보내고 받는 쪽이 그것을 쓴다**
- [ ] **워크렛이 없으면 rAF 로 물러선다.** 로드 실패나 `AudioContext` 가 아직 없는 상태에서도 아무것도 안 도는 상황을 만들지 않는다. 오디오가 켜지면 워크렛이 이어받고 rAF 구동은 끈다 (둘이 동시에 돌면 분석이 두 번 실행된다)
- [ ] 씬 입력을 한 곳에서 만든다. 중앙 무대와 출력 창이 각자 모으면 한쪽만 고쳐져 화면이 갈린다
  - `public/` 에 두지 않는다. 파일 구조가 갈리고, 고정 경로라 브라우저가 낡은 파일을 캐시할 수 있다
  - 별도 빌드 단계를 만들지 않는다. **빌드를 깜빡하면 낡은 워크렛이 조용히 도는 실패 방식이 생긴다.** 공연 중에 이런 실패는 원인을 못 찾는다
- [ ] 분석 루프의 구동원을 콘솔의 `requestAnimationFrame` 에서 이 메시지로 바꾼다. `analyze()` 안은 건드리지 않는다
- [ ] 콘솔의 rAF 는 콘솔 미리보기와 수치 표시에만 쓴다. 여기가 멈춰도 무대는 영향을 받지 않아야 한다
- [ ] 출력 창이 자기 rAF 로 그리게 한다. 콘솔이 보낸 값을 받아 자기 창에서 그린다
- [ ] 출력 창이 0.5초 이상 값을 못 받으면 마지막 값으로 계속 그린다. **화면에 오류 표시를 띄우지 않는다** — 관객이 보는 화면이다
- [ ] 시각(`S.time`)의 기준을 콘솔 rAF 가 아니라 `AudioContext.currentTime` 으로 바꾼다. rAF 가 멈추면 시간도 멈추기 때문이다

## 이 방식이 안 통하면

실제로 최소화해 보고 메인 스레드가 멈추면 그때는 워크렛에서 시간영역 샘플을 받아 FFT 를 직접 하는 수밖에 없습니다. **그 경우 온셋 임계값과 BPM 계수를 전부 다시 맞춰야 하므로 별도 이슈로 뺍니다.** 먼저 위 방식으로 재 보고 결과를 알려 주십시오.

## 완료 기준

- [ ] **출력 창을 열어 둔 채 콘솔을 최소화하면 출력 화면이 계속 움직인다**
- [ ] 콘솔을 다시 열었을 때 음악과 맞는 자리에서 이어진다. 멈춰 있던 만큼 뒤처지지 않는다
- [ ] 콘솔을 다른 탭 뒤로 보내도 같다
- [ ] 출력 창을 최소화하면 출력만 멈추고 콘솔은 계속 돈다 (이건 정상이다)
- [ ] 두 창이 모두 보이는 정상 배치에서 60fps 가 유지된다. 워크렛으로 옮기면서 프레임이 떨어지지 않았다
- [ ] 콘솔의 분석 리드아웃 수치가 예전과 같다. 워크렛 이전으로 값이 달라지지 않았다

## 검증

`music/knockout.mp3` 를 재생하고 출력 창을 두 번째 화면에 띄운 뒤 콘솔을 최소화한다. 20초 뒤 콘솔을 다시 열어, 출력 화면의 비트가 음악과 맞는지 본다.

값이 달라지지 않았는지는 워크렛 이전 전후로 09 리드아웃을 같은 구간에서 비교한다.
