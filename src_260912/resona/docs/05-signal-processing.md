# 05. 신호처리 명세

이 문서의 파라미터는 기존 프로토타입(`resona.html`, `audience-energy-demo.html`)에서 실제로 쓰이던 값을 옮긴 것입니다. 임의로 정한 값이 아니므로, 바꾸기 전에 왜 그 값인지 먼저 확인하시기 바랍니다.

---

## 1. 오디오 그래프

신호 자체를 mid / side 로 변환한 뒤 각각 분석합니다. 좌우 채널을 그대로 분석하고 크기 스펙트럼을 빼는 방식은 쓰지 않습니다. 이유는 2-1절에 있습니다.

```
소스 (파일 · 마이크 · 데모)
  │
  ├─▶ ChannelSplitter ─┬─▶ Gain(+0.5) ─┐
  │                    │               ├─▶ Merge ─▶ AnalyserNode(mid)
  │                    └─▶ Gain(+0.5) ─┘
  │                    │
  │                    ├─▶ Gain(+0.5) ─┐
  │                    │               ├─▶ Merge ─▶ AnalyserNode(side)
  │                    └─▶ Gain(-0.5) ─┘
  │
  └─▶ GainNode(master) ─▶ destination
```

Web Audio 에서는 `GainNode` 의 `gain` 에 음수를 넣을 수 있으므로, 오른쪽 채널에 `-0.5` 를 걸어 같은 노드로 합류시키면 `(L - R) × 0.5` 가 만들어집니다.

| 설정 | 값 | 이유 |
|---|---|---|
| `fftSize` | 4096 | 48kHz 기준 주파수 해상도 약 11.7Hz. 저역 구분에 필요합니다 |
| `smoothingTimeConstant` | 0.0 (기본 분석) | 평활은 상위 단계에서 하므로 여기서는 원값을 씁니다 |
| 스템용 `fftSize` | 1024 | 스템은 세기만 보므로 해상도가 낮아도 됩니다 |
| 스템용 `smoothingTimeConstant` | 0.5 | |

마이크 입력은 다음 제약을 반드시 끕니다. 공연 음향을 있는 그대로 재야 하기 때문입니다.

```ts
getUserMedia({
  audio: {
    echoCancellation: false,
    noiseSuppression: false,
    autoGainControl: false,
  }
})
```

마이크 입력은 스피커로 되돌리지 않습니다. 하울링이 납니다.

## 2. 기본 특징 추출

매 분석 프레임에서 다음을 계산합니다.

### 2-1. mid / side

1절의 그래프에서 만든 두 신호의 주파수 크기를 그대로 씁니다.

```
mid  신호 = (L + R) × 0.5   →  AnalyserNode →  mid[i]
side 신호 = (L - R) × 0.5   →  AnalyserNode →  side[i]
```

`mid` 는 중앙에 정위된 성분(보컬, 킥, 베이스)이 강하고, `side` 는 좌우로 벌린 성분(신스, 리버브, 기타)이 강합니다. 이 차이를 스템 추정에 씁니다.

**크기 스펙트럼끼리 빼는 방식은 쓰지 않습니다.** 좌우 채널을 따로 분석해 얻은 크기 `l`, `r` 로 `side = |l - r|` 을 계산하면, 위상이 반대이고 크기가 같은 성분에서 `side` 가 정확히 0 이 됩니다. 크기 스펙트럼에는 위상 정보가 없기 때문입니다. 실제 음악에서도 좌우 크기 스펙트럼은 거의 같아서 `side` 가 늘 0 근처에 머물고, 결과적으로 OTHER 스템이 죽습니다.

신호 영역에서 먼저 빼면 위상이 반영되어 좌우로 벌어진 성분이 `side` 에 그대로 남습니다.

### 2-2. 스펙트럴 플럭스

이전 프레임 대비 증가분만 더합니다. 감소는 무시합니다. 소리가 새로 시작되는 순간을 잡는 것이 목적이기 때문입니다.

```
flux = Σ max(0, mid[i] - prevMid[i]) / N × 42
```

계수 42 는 값을 0~1 대역으로 끌어올리기 위한 배율입니다.

동시에 두 가지 부분 플럭스를 따로 모읍니다.

- `fluxHi` — HI·AIR 밴드 구간의 증가분. 하이햇과 스네어의 지표
- `fluxKick` — SUB·LOW 밴드 구간의 증가분. 킥의 지표

### 2-3. RMS 와 피크

시간 영역 샘플을 두 칸씩 건너뛰며 계산합니다. 전수 계산은 불필요하게 무겁습니다.

```
rms = sqrt( Σ v² / (n/2) )
A.rms = lerp(A.rms, clamp(rms × 3.2, 0, 1), 0.35)

peakDecay = max(peakDecay × 0.985, |v|max)
```

`3.2` 는 일반적인 공연 음원의 RMS 를 0~1 로 펼치기 위한 배율이고, `0.985` 는 피크가 천천히 떨어지게 하는 감쇠 계수입니다.

`lerp(..., 0.35)` 는 60fps 기준 시정수 약 40ms 입니다. 킥마다 값이 크게 오르내립니다.

**상태 판정용으로 세 번째 값을 따로 둡니다.**

```
rmsSlow += (A.rms − rmsSlow) × (1 − exp(−dt / 0.4))
```

세 값의 쓰임이 다릅니다. 섞어 쓰면 안 됩니다.

| 값 | 시정수 | 성격 | 쓰는 곳 |
|---|---|---|---|
| `A.rms` | 40ms | 순간값 | 밝기·밀도 등 연출 파라미터, `SILENT`, `BREAK` |
| `rmsSlow` | 0.4초 | 평활값 | **상태 판정의 `PEAK`** |
| `peakDecay` | 약 1.1초 | 피크 **홀드** | 화면 표시용 피크 미터 |

`peakDecay` 를 상태 판정에 쓰면 안 됩니다. 평활이 아니라 홀드라서 한 번 세게 친 뒤 오래 내려오지 않고, 센 구간과 보통 구간이 갈리지 않습니다.

### 2-4. 스펙트럴 센트로이드

주파수 크기의 무게중심입니다. 음색의 밝기를 나타내며 색상 결정에 씁니다.

```
centroid = (Σ mid[i] × i / Σ mid[i]) × (sampleRate / 2 / N)
```

단위는 Hz 입니다.

### 2-5. 6밴드 에너지

| 밴드 | 범위 | 성격 |
|---|---|---|
| SUB | 20–60 Hz | 초저역, 몸으로 느끼는 대역 |
| LOW | 60–250 Hz | 킥과 베이스 |
| LMID | 250–500 Hz | 저중역, 두께 |
| MID | 500–2000 Hz | 보컬 기본음 |
| HI | 2000–6000 Hz | 명료도, 어택 |
| AIR | 6000–16000 Hz | 공기감, 심벌 |

각 밴드의 평균을 구한 뒤 `clamp(raw × 1.55, 0, 1)` 로 정규화하고 `lerp(..., 0.4)` 로 평활합니다.

## 3. 온셋과 템포

### 3-1. 온셋 검출

고정 임계값은 곡의 음량에 따라 무너집니다. 최근 이력의 중앙값을 기준으로 잡는 적응 임계값을 씁니다.

```
fluxHist 에 최근 52 프레임의 flux 를 유지
med  = fluxHist 를 정렬한 뒤 55 퍼센타일 위치의 값
thr  = med × 1.5 + 0.022

isOnset = (flux > thr)
       && (now - lastOnsetT > 0.085)   // 최소 간격 85ms
       && (rms > 0.035)                // 무음 구간의 오검출 차단
```

세 조건을 모두 만족해야 온셋으로 인정합니다. 85ms 는 사람이 별개의 타격으로 구분하는 최소 간격에 가깝습니다.

### 3-2. 온셋 엔벨로프

BPM 추정을 위해 온셋의 세기를 100Hz 고정 주기로 원형 버퍼에 쌓습니다. 화면 갱신 주기는 기기마다 다르므로, 분석 주기를 고정하지 않으면 템포 추정이 기기에 따라 달라집니다.

```
ENV_HZ = 100
envAcc = max(envAcc, max(0, flux - med))

매 1/100 초마다:
  envBuf[envIdx] = envAcc
  envIdx = (envIdx + 1) % envBuf.length
  envAcc *= 0.4          // 누적값을 줄여 다음 구간에 번지지 않게 합니다
```

### 3-3. BPM 추정

0.4초마다, 버퍼가 400 샘플 이상 찼을 때 실행합니다.

**1단계 — 평균 제거 후 자기상관**

```
e[i] = envBuf[i] - mean(envBuf)
r[lag] = Σ e[i] × e[i-lag] / (n - lag)
```

`lag` 범위는 60~200 BPM 에 해당하는 구간이며, 배음 확인을 위해 최대 지연의 4배까지 미리 구합니다.

**2단계 — 빗살 점수**

자기상관의 단일 최대값만 쓰면 8분음표 주기나 2마디 주기에 걸리는 일이 잦습니다. 배음을 함께 보는 빗살 점수로 진짜 박 주기를 고릅니다.

```
score(lag) = r[lag]
           + r[lag×2] × 0.62
           + r[lag×3] × 0.38
           + r[lag×4] × 0.22
```

> 빗살 점수는 정박의 1.5배 후보(점 4분음표 자리)를 걸러내지 못합니다. 자기상관 원값에 최소 조건을 거는 방법을 시도했으나 실제 음악에서 오답 후보의 원값이 오히려 1위인 경우가 있어 효과가 없었습니다. 경위와 다음 시도 후보는 `issues/10-tempo-accuracy.md` 에 있습니다. 실사용에서는 `02-features.md` F-303-2(탭 템포·잠금)로 대응합니다.

**3단계 — 템포 연속성 가중**

이전에 잡은 BPM 과 가까운 후보에 가산점을 줍니다. 곡 중간에 템포가 튀는 것을 막습니다.

```
if (이전 BPM > 0):
  cand = 60 × ENV_HZ / lag
  score *= 1 + 0.30 × bpmConf × exp(-|cand - 이전BPM| / 5.5)
```

**가중에 `bpmConf` 를 곱하는 것이 중요합니다.** 이것이 빠지면 분석 창이 짧은 초반에 우연히 앞선 후보가 자기 자신을 계속 강화해, 같은 곡을 틀어도 실행마다 다른 BPM 에 고착됩니다. 신뢰도가 낮은 동안에는 가중이 거의 걸리지 않아 순수 점수로 판정하고, 값이 안정된 뒤에야 연속성이 힘을 갖는 구조여야 합니다.

**4단계 — 옥타브 접기와 갱신**

```
bpm = 60 × ENV_HZ / bestLag
while (bpm < 72)  bpm *= 2
while (bpm > 182) bpm /= 2

갱신 폭:
  이전 BPM 이 0 이면            → 그대로 채택
  차이가 2.2 BPM 을 넘으면      → lerp(이전, 새값, 0.30)
  그보다 작으면                → lerp(이전, 새값, 0.10)
```

큰 차이는 빠르게 따라가고 작은 차이는 천천히 따라가는 구조입니다. 표시 화면이 소수점에서 떨리지 않게 합니다.

### 3-4. 비트 트래킹

BPM 이 잡히면 주기를 예측하고, 온셋이 예측 근처에 오면 위상을 맞춥니다.

```
per = 60 / bpm

if (isOnset && |now - nextBeatT| < per × 0.30):
    nextBeatT = now              // 위상 스냅

if (now >= nextBeatT):
    fireBeat()
    nextBeatT += per
    if (now - nextBeatT > per):  // 너무 밀렸으면 재동기화
        nextBeatT = now + per

phase = clamp(1 - (nextBeatT - now) / per, 0, 1)
```

BPM 이 아직 없으면 온셋이 올 때마다 비트로 취급하되 최소 간격 0.28초를 둡니다.

비트가 발생할 때마다 `beatInBar` 를 1~4 로 돌리고, 1 이 될 때 `bar` 를 올립니다.

**BPM 이 바뀌어도 이미 센 마디는 다시 계산하지 않습니다.** 바뀐 시점부터 새 주기로 이어 셉니다. 지금까지 흐른 시간을 새 BPM 으로 소급해 다시 나누면 마디 번호가 갑자기 뛰어, 공연 중 오퍼레이터가 위치를 잃습니다.

**무음에서는 박을 찍지 않습니다.** 위 구조는 `bpm` 이 0 이 아니면 소리가 있든 없든 예측만으로 계속 박을 찍습니다. 순간적으로 음량이 줄어도 비트가 끊기지 않게 하려는 설계이지만, 그대로 두면 곡이 끝난 뒤에도 마디와 박이 계속 올라갑니다.

```
silenceT = (rms < 0.02) ? silenceT + dt : 0

if (silenceT > 2.0):
    비트 찍기 중단        // fireBeat 호출하지 않음
    phase 갱신 중단
    bpm 값은 유지         // 소리가 돌아오면 곧바로 이어서 씁니다
else:
    정상 동작
```

소리가 돌아오면 `nextBeatT` 를 현재 시각 기준으로 다시 잡고 이어서 찍습니다. 2초라는 값은 곡 중간의 브레이크(보통 4초 이하)에서 BPM 자체는 유지하면서, 소리가 없는 동안 화면이 혼자 박자를 치는 것만 막는 기준입니다.

### 3-5. 분석 상태 초기화

**재생을 새로 시작할 때 템포 관련 상태를 전부 비웁니다.** 이것이 빠지면 이전 재생에서 쌓인 엔벨로프가 새 곡의 앞부분과 섞여, 같은 곡인데도 실행마다 다른 BPM 이 나옵니다. 증상은 뚜렷합니다. *정상이라면 재생 후 4~5초 동안 BPM 이 비어 있어야 하는데, 시작하자마자 값이 뜨고 곡이 진행되면서 서서히 다른 값으로 옮겨 갑니다.*

비울 것은 다음과 같습니다.

```
envBuf 전체 0, envIdx = 0, envFilled = 0, envAcc = 0, envAccT = 0
fluxHist = []
bpm = 0, bpmConf = 0, bpmTimer = 0
nextBeatT = 0, beat = 0, bar = 1, beatInBar = 1, phase = 0
prevMid 전체 0
스템 AGC 전체 초기값
```

호출 시점은 네 곳입니다.

- 새 파일을 로드했을 때
- 정지(stop) 했을 때
- **재생이 끝까지 진행되어 자연히 종료됐을 때** (`ended` 이벤트)
- 탐색(seek) 했을 때 — 다만 **부분 초기화**입니다. 아래 설명을 보십시오
- 입력 소스를 바꿨을 때 (파일 ↔ 마이크 ↔ 데모)

일시정지(pause)에서는 비우지 않습니다. 같은 위치에서 이어지므로 버퍼가 유효합니다.

**탐색은 부분 초기화입니다.** 시간이 건너뛰면 엔벨로프가 불연속이 되므로 버퍼와 비트 위상은 비워야 합니다. 그러나 *같은 곡 안에서 위치만 옮긴 것이므로 템포는 그대로입니다.* `bpm` 과 `bpmConf` 까지 지우면, 리허설에서 구간 반복(F-202)으로 A·B 를 찍을 때마다 템포를 처음부터 다시 찾느라 그때그때 다른 값이 나옵니다.

```
탐색 시 비울 것   : envBuf · envIdx · envFilled · envAcc · envAccT
                   fluxHist · prevMid · nextBeatT · phase
탐색 시 유지할 것 : bpm · bpmConf · bar · beat
```

새 파일 로드·정지·자연 종료·소스 전환에서는 `bpm` 을 포함해 전부 비웁니다.

## 4. 스템 추정

실제로 분리된 스템 파일이 있으면 각 파일의 RMS 를 그대로 씁니다. 없으면 신호처리로 근사합니다. 딥러닝 분리는 지연 때문에 쓰지 않습니다.

```
drumRaw = fluxHi × 1.7 / N × 40 + fluxKick × 2.4 / N × 40
bassRaw = (bandsRaw[SUB] × 1.15 + bandsRaw[LOW]) × 0.62
vocRaw  = 200~4000Hz 구간에서 mean( max(0, mid[i] - side[i] × 1.05) )
othRaw  = 150~14000Hz 구간에서 mean( side[i] ) × 1.6
```

`bassRaw` 에는 **`bands` 가 아니라 `bandsRaw`** 를 넣습니다. `bands` 는 이미 1.55 배율과 0~1 클램프를 거친 표시용 값이라, 요즘 마스터링된 음원에서는 저역이 상시 1.00 에 붙습니다. 그 위에서 다시 계산하면 BASS 스템이 항상 최대에 고정됩니다.

보컬은 중앙 정위 성분에서 좌우로 벌어진 성분을 뺀 것으로 근사합니다. 기타 성분은 반대로 좌우로 벌어진 쪽을 씁니다.

각 값은 채널별 자동 이득 조절로 정규화합니다.

```
agc[k] = max(raw[k], agc[k] × 0.9990, 0.03)   // 추정 스템
agc[k] = max(rms[k], agc[k] × 0.9985, 0.02)   // 실제 스템
value  = clamp(raw[k] / agc[k], 0, 1)
```

평활 계수는 드럼만 빠르게(0.55), 나머지는 느리게(0.28) 둡니다. 드럼은 순간적인 타격을 놓치면 의미가 없기 때문입니다.

**전체 레벨이 낮으면 스템을 0 으로 둡니다.**

AGC 는 최근 최댓값 대비 지금 값을 재는 구조라 **입력이 조용한지 아닌지를 모릅니다.** 마이크로 조용한 방을 받으면 저주파 암소음(공조, 팬, 건물 진동, 마이크 자체 잡음)만 들어오는데, `bassRaw` 가 0.025 여도 `agc` 가 하한 0.03 에 머물러 있으므로 `0.025 / 0.03 = 0.83` 이 나옵니다. 전체 RMS 는 0.01 인데 BASS 스템만 0.83 으로 뜨는 상태가 됩니다.

```
STEM_GATE = 0.015
if (rmsSlow < STEM_GATE) stems = [0, 0, 0, 0]
```

게이트가 걸린 동안에는 **원값을 AGC 에 먹이지도 않습니다.** 먹이면 암소음이 기준을 잡아 버려서, 게이트가 열리는 순간 그 기준으로 음악을 잽니다. 감쇠와 하한만 그대로 돌립니다.

```
agc[k] = max(agc[k] × 0.9990, 0.03)          // 게이트가 걸린 동안
```

#### 순간값 `rms` 가 아니라 `rmsSlow` 를 봅니다

명세 초안은 `rms` 로 적혀 있었으나 실측하고 바꿨습니다. 조용한 방은 레벨이 문턱 근처에서 계속 오르내리므로, 순간값으로 재면 게이트가 매 프레임 열렸다 닫힙니다. 「공조가 도는 홀」 14초 동안 `rms` 로는 **56회**, `rmsSlow` 로는 **5회** 뒤집혔습니다. 스템이 초당 네 번 켜졌다 꺼지면 잡음을 따라가는 것과 다를 바 없습니다.

`rmsSlow` 는 시상수 0.4초 평활값이고(2-3절), 이미 `PEAK` 판정이 같은 이유로 이 값을 씁니다.

#### 네 조건 실측

`bassRaw` 는 조용한 방에서도 0.31 까지 나오는데 AGC 하한이 0.03 이라 그대로 BASS 스템 0.8 이 됩니다. 문턱을 정하려고 네 조건에서 `rms` 와 `rmsSlow` 를 같이 쟀습니다. 마이크 조건 셋은 `getUserMedia` 를 가로채 같은 음원을 흘려 넣었고, ④ 만 파일 재생입니다. 표본 간격 55ms · 조건당 14초.

| ① 조용한 방 — 공조가 도는 홀 | 244 | 0.0092 / 0.0132 / 0.0262 | 0.0115 / 0.0135 / 0.0169 | **0.87** | 93% | 0.87 |

**「①의 최댓값과 ②·④의 최솟값 사이」로는 정해지지 않습니다.** ④ 의 프레임 최솟값 0.0060 은 악구와 악구 사이의 정적이라 어떤 문턱보다도 아래에 있습니다. 그 자리에서 스템이 0 이 되는 것은 옳은 동작이지 손실이 아닙니다. 그래서 최솟값 대신 **눌리는 프레임이 무엇을 들고 있었는지**로 갈랐습니다. 오른쪽 두 열이 그 판정입니다.

- ① 에서 눌리는 프레임은 BASS **0.81~0.87** 을 들고 있었습니다. 이것이 없애야 할 값입니다.
- ④ 에서 눌리는 프레임은 BASS **0.13~0.14** 였습니다. 남는 프레임의 BASS 중앙(0.21~0.23)은 그대로입니다. **발라드의 음악은 죽지 않습니다.**
- ③ 은 한 프레임도 눌리지 않습니다.

0.015 를 고른 이유는 위 항목의 「공조가 도는 홀」입니다. 조용한 홀만 보면 0.010 으로 충분하고 ② 도 하나 잃지 않지만, 그러면 공조가 도는 홀에서 3% 밖에 눌리지 않아 게이트가 사실상 없는 것이 됩니다. 이 절 앞의 서술이 드는 예(`rms` 0.01)도 0.010 으로는 반만 걸립니다.

**② 는 원리적으로 갈리지 않습니다.** 음악을 암소음과 같은 레벨까지 줄이면 절대 레벨로는 구별할 방법이 없습니다. 0.015 에서 ② 의 20% 가 눌리고, 그 프레임의 BASS 0.38 은 상당 부분 밑에 깔린 암소음이 만든 값입니다. 현장 처방은 문턱이 아니라 입력 게인입니다 — 콘솔에 들어오는 레벨을 올리면 ② 는 ③ 쪽으로 옮겨 갑니다.

스템 출력에는 평활(드럼 0.55, 나머지 0.28)이 걸려 있어서, 한두 프레임 눌린 것만으로는 0 으로 떨어지지 않습니다. 게이트가 이어질 때만 실제로 0 이 됩니다. 게이트를 붙인 뒤 다시 재니 표시값이 0.00 으로 유지된 프레임 비율은 ① 100% / 89%, ② 2%, ③ 0%, ④ 21% / 6% / 0% 였습니다.

#### 문턱 근처에서 세로실이 깜빡이지 않습니다

② 는 20% 가 눌리는 조건이므로 게이트가 계속 열리고 닫힙니다. 그때 세로실이 깜빡이면 히스테리시스가 필요합니다. 같은 음원을 흘리면서 문턱만 바꿔 짝지어 쟀습니다 (구간 4초 · 6라운드 · 캔버스 가로 스캔라인의 밝은 상위 5% 와 바탕의 차를 매 프레임).

| 조건 | 세로실 대비 중앙 | 가장 어두운 10% 프레임 |
|---|---|---|
| A 게이트 없음 | 30.7 ± 5.9 | 13.00 ± 0.84 |
| B 0.015 (지금) | 27.2 ± 4.5 | 12.08 ± 0.36 |
| E 0.0205 — ② 의 중앙값. 교차가 최대인 자리 | 35.0 ± 5.1 | 10.40 ± 0.37 |

깜빡임은 「가장 어두운 10% 프레임」에 나타납니다. 세로실이 잠깐 가늘어지면 그 프레임의 대비가 떨어지기 때문입니다.

- **B − A = −0.93 ± 1.10 (t = −0.84, 6짝 중 3짝)** — 게이트를 걸지 않은 것과 구별되지 않습니다.
- **E − A = −2.60 ± 1.09 (t = −2.39, 6짝 중 5짝에서 감소)** — 양성 대조는 잡힙니다.

양성 대조가 잡히므로 측정이 깜빡임에 눈감은 것이 아닙니다. **0.015 에서는 깜빡이지 않습니다.** 히스테리시스를 넣지 않았습니다.

두 가지가 겹쳐 그렇습니다. 스템 출력에 평활(0.28)이 걸려 한두 프레임 눌린 것으로는 0 까지 내려가지 않고, 세로실 굵기 `v = (mlv × 0.5 + stems[g] × 0.5)^1.45` 의 절반이 행 이력(`mlv`)이라 게이트가 움직일 수 있는 몫이 절반뿐입니다. 130ms 간격 연속 프레임 여덟 장에서도 세로실이 켜졌다 꺼지는 자리는 보이지 않았습니다.

넣게 된다면 열림 0.015 / 닫힘 0.012 입니다. 그 조건도 같이 쟀는데 A 와 구별되지 않았습니다 (t = +0.95).

**직조 씬 확인.** 게이트를 켠 상태에서 조용한 방을 마이크로 받으면 02 스템 네 칸이 모두 0.00 이 되고, 세로실이 사라져 가로실만 희미하게 남습니다. 잡음을 따라 굵기가 흔들리던 세로실이 없어졌습니다. 정상 볼륨(③)에서는 세로실·가로실이 그대로 짜이고 BPM 도 120 으로 잡힙니다.

한 가지 남습니다. 게이트는 스템만 다루므로 **BPM 추정은 여전히 잡음에서 돌아갑니다** — 조용한 방에서 BPM 109·113 이 표시됩니다. 신뢰도가 낮게 나오지만 숫자 자체는 뜹니다. 이것은 이 게이트의 몫이 아니고 별도 과제입니다.

AGC 하한을 올리는 방식으로는 풀리지 않습니다. 하한을 올리면 진짜로 조용한 곡에서 스템이 나오지 않습니다. 조용한 *곡*과 조용한 *입력*은 다른 것이고, 이 둘을 가르는 것은 상대 비율이 아니라 절대 레벨입니다.

**파일 재생에서는 드러나지 않는 자리입니다.** 디코딩된 신호는 무음 구간의 바닥이 0 에 가깝지만 마이크는 언제나 암소음이 있습니다. 실제 공연에서 곡과 곡 사이 정적에 BASS 가 0.8 로 튀면, 직조 씬의 세로실 굵기와 연출 파라미터가 그 잡음을 따라갑니다.

이 특성은 원본 프로토타입에도 있습니다 (`stemAgc[k] = Math.max(r2, stemAgc[k]*.9985, .02)`). 파일 재생이 주였고 마이크로 조용한 방을 오래 들여다볼 일이 없어 드러나지 않았을 뿐입니다. F-102 를 붙이면서 비로소 보이게 된 자리입니다.

## 5. 관객 에너지

두 방식 모두 최종적으로 0~1 의 `audienceEnergy` 하나를 냅니다. 인터페이스는 `02-features.md` F-300 을 따릅니다.

### 5-1. 카메라 모션 방식

**축소** — 영상을 64×36 격자(2,304칸)로 줄입니다. 원본 프레임은 즉시 버립니다.

```
L = 0.299R + 0.587G + 0.114B     // 휘도 변환
```

**전역 밝기 변화 제거** — 조명이 바뀌면 화면 전체가 변합니다. 이것을 관객의 움직임으로 오인하면 안 됩니다.

```
shift = (현재 프레임 평균 휘도 - 이전 프레임 평균 휘도)

각 칸에서:
  d = |(cur[i] - prev[i]) - shift| / 255
  v = d > 0.012 ? d : 0          // 센서 잡음 바닥값
  field[i] += (v - field[i]) × 0.30   // 칸 단위 평활
  
raw = mean(v)
```

`0.012` 아래는 카메라 센서의 잡음으로 보고 버립니다.

### 5-2. 마이크 오디오 방식

```
clapRaw  = 2000~8000Hz 구간의 트랜지언트 밀도
cheerRaw = 300~4000Hz 구간의 지속 에너지
raw = clapRaw × 0.6 + cheerRaw × 0.4
```

무대 음향이 섞여 들어오는 문제가 있습니다. 음악 트랙의 스펙트럼과 상관이 높은 성분을 감쇠해 완화합니다.

```
corr = 음악 스펙트럼과 관객 스펙트럼의 상관계수 (0~1)
raw *= (1 - corr × 0.7)
```

이 보정은 완전하지 않습니다. 객석 마이크를 무대에서 멀리 두는 물리적 배치가 더 중요합니다.

### 5-3. 자동 보정

공연장마다 기준이 다르므로 최근 60초의 분포로 정규화합니다.

```
history 에 최근 1800 샘플 유지 (30fps 기준 60초)
15 샘플마다, 60 샘플 이상 쌓였을 때 갱신:
  lo = 정렬한 history 의 5 퍼센타일
  hi = 정렬한 history 의 95 퍼센타일

normalized = clamp((raw - lo) / max(hi - lo, 1e-5), 0, 1)
```

600 샘플(20초)이 쌓이면 보정 완료로 표시합니다. 그 전까지는 진행률을 보여 줍니다.

**재보정은 이력만 비웁니다. 입력 소스를 재시작하지 않습니다.**

```
recalibrate() {
  history.length = 0;   // 분포만 버립니다
  // 카메라 스트림, 마이크 트랙, 권한은 그대로 둡니다
}
```

소스를 통째로 다시 시작하면 `getUserMedia` 가 다시 호출되어 스트림이 끊기고, 브라우저에 따라 권한을 다시 묻습니다. 공연 중에 재보정 한 번으로 카메라가 죽습니다. 재보정은 "지금 이 순간을 새 기준으로 삼는다"는 뜻이지 "장치를 다시 연다"는 뜻이 아닙니다.

**시뮬레이션은 보정을 건너뜁니다.** 시뮬은 이미 0~1 로 값을 만들므로 정규화할 대상이 없고, 20초를 기다리게 하면 "카메라 없이 개발한다"는 목적에 어긋납니다. 어택·릴리스 평활은 그대로 겁니다.

> **5단계 검증에서 유의할 점** — 시뮬이 보정을 건너뛰므로, 시뮬만으로 연출 결합을 확인하면 보정 경로가 한 번도 실행되지 않습니다. 보정 자체의 결함은 카메라나 마이크로만 잡힙니다. 5단계 완료 확인은 두 경로로 각각 한 번씩 하시기 바랍니다.

### 5-4. 어택·릴리스 평활

관객 반응은 빠르게 오르고 천천히 식습니다. 오르내림에 다른 시정수를 씁니다.

```
ATTACK_TAU  = 1.5초   // 오를 때
RELEASE_TAU = 3.0초   // 내릴 때

tau = (target > smooth) ? ATTACK_TAU : RELEASE_TAU
smooth += (target - smooth) × (1 - exp(-dt / tau))
```

이 비대칭이 중요합니다. 같은 시정수를 쓰면 박수가 끝나자마자 화면이 꺼져 어색합니다.

### 5-5. 상태 구간

| 구간 | 범위 | 표시 |
|---|---|---|
| DORMANT | 0.00 ~ 0.25 | 잠잠함 |
| STIRRING | 0.25 ~ 0.50 | 술렁임 |
| ACTIVE | 0.50 ~ 0.75 | 활발함 |
| SURGE | 0.75 ~ 1.00 | 폭발 |

## 6. 연출 번역 — 두 신호가 합쳐지는 곳

**이 절이 프로젝트의 핵심입니다.** 기존 프로토타입에서 비어 있던 자리이며, 여기를 구현하지 않으면 오디오 비주얼라이저와 다를 것이 없습니다.

### 6-1. 음악 상태 판정

```ts
type MusicState = 'SILENT' | 'CALM' | 'GROOVE' | 'BUILD' | 'PEAK' | 'BREAK';
```

판정 규칙입니다. 위에서부터 먼저 맞는 것을 채택합니다.

| 순서 | 상태 | 조건 | 판정에 쓰는 값 |
|---|---|---|---|
| 1 | `SILENT` | `rms < 0.04` 가 0.5초 이상 지속 | `rms` (빠른 값) |
| 2 | `BREAK` | `rms` 가 직전 2초 평균의 45% 아래로 급락 | `rms` (빠른 값) |
| 3 | `BUILD` | `rmsSlope > 0.008` | `rms` 3초 회귀 |
| 4 | `PEAK` | `rmsSlow > 0.434` | `rmsSlow` (2-3절) |
| 5 | `GROOVE` | `bpmConf > 0.45` 이고 비트가 규칙적 | |
| 6 | `CALM` | 위에 해당하지 않음 | |

#### BUILD 를 PEAK 보다 먼저 검사합니다

**세기 하나로는 `BUILD` 와 `PEAK` 이 원리적으로 갈리지 않습니다.** 빌드업은 정의상 정점 직전에 가장 커지므로, 빌드업 끝의 세기가 정점 초반과 비슷하거나 오히려 큽니다. 실측에서도 `BUILD` 구간 최대 `rmsSlow` 가 0.558 로 `PEAK` 구간 대부분(0.44~0.49)보다 컸습니다.

두 구간을 가르는 것은 세기가 아니라 **기울기의 부호**입니다.

| 구간 | `rmsSlow` 중앙 | `rmsSlope` 중앙 |
|---|---|---|
| BUILD | 0.471 | **+0.013** (오르는 중) |
| PEAK | 0.485 | **−0.009** (다 올라옴) |

`PEAK` 을 먼저 검사하면 빌드업 후반이 `BUILD` 가 될 기회 없이 `PEAK` 으로 넘어갑니다. 순서를 바꾸면 "아직 오르는 중이면 빌드업, 다 올라왔으면 정점"이 됩니다.

#### PEAK 판정 입력은 `rmsSlow` 입니다

`A.rms` 는 시정수 40ms 라 킥마다 0.31 과 0.93 사이를 오갑니다. 순간값으로 "이 구간이 센가"를 물으면 조건이 한 프레임도 이어지지 않습니다.

`peakDecay` 도 쓰지 않습니다. 평활이 아니라 홀드라서 한 번 세게 친 뒤 계속 높게 남습니다. 실측에서 `GROOVE` 구간에도 0.97 이 나왔습니다.

시정수 0.4초의 `rmsSlow` 가 맞습니다. 킥 단위 요동은 걷어내면서 구간 차이는 남깁니다. 120 BPM 기준 킥 간격이 0.5초이므로, 0.4초는 킥 하나로 다 내려가지 않고 구간이 바뀌면 따라가는 길이입니다.

`SILENT` 와 `BREAK` 은 빠른 `A.rms` 를 그대로 씁니다. 느린 값으로 급락을 재면 브레이크를 놓칩니다.

#### PEAK 에서 `bands[HI]` 조건을 뺐습니다

원래 조건은 `rms > 0.72` 이고 `bands[HI] > 0.6` 이었습니다. 두 가지 이유로 뺍니다.

**역할이 겹칩니다.** `PEAK` 은 "가장 센 구간"이지 "밝은 구간"이 아닙니다. 음색의 밝기는 7절의 `valence` 가 전담하고, 격렬함을 재는 `arousal` 산식에도 `bands[HI]` 가 이미 0.18 가중으로 들어 있습니다. 상태 판정이 음색까지 겸하면 같은 값을 두 곳에서 쓰는 셈이 됩니다.

**문턱이 실제로 안 넘어갑니다.** HI 는 2000~6000Hz 인데, 신스로 만든 검증 음원은 배음이 적어 가장 센 순간에도 0.44~0.51 에 머뭅니다. 실측 근거 없이 정한 0.6 이었습니다.

#### 문턱 두 개는 실측으로 정했습니다

`synth/test-03-buildup.wav` 를 재생하며 초당 한 번씩 기록한 분포입니다.

| 기대 구간 | n | `rmsSlow` 중앙 / 최대 | `rmsSlope` 중앙 |
|---|---|---|---|
| CALM (4~16초) | 12 | 0.251 / 0.252 | 0.000 |
| GROOVE (16~30초) | 14 | 0.387 / **0.423** | 0.003 |
| BUILD (30~42초) | 12 | 0.471 / 0.558 | **0.013** |
| PEAK (42~50초) | 8 | 0.485 / 0.722 (최소 **0.444**) | −0.009 |

```
PEAK_TH  = 0.434    // GROOVE 최대 0.423 과 PEAK 최소 0.444 사이의 빈 자리
SLOPE_TH = 0.008    // GROOVE 중앙 0.003 과 BUILD 중앙 0.013 의 가운데
```

이 순서와 조건으로 상태 순서를 다시 재면 `BUILD` 가 33초부터 12.1초, `PEAK` 이 44.4초부터 8.1초 이어지고 깜빡임이 없습니다. `PEAK` 시작이 기대(42초)보다 2.4초 늦는 것은 42~43초의 기울기가 아직 양수(+0.116, +0.054)라 `BUILD` 로 잡히기 때문이며, "정점에 다 올라온 시점"이라는 뜻이므로 규칙대로입니다.

`music/knockout.mp3` 로 교차 확인했습니다. `rmsSlow` 가 중앙 0.238 과 p75 0.508 두 덩어리로 갈리고 0.434 가 그 사이 빈 자리에 들어갑니다. 문턱을 0.40~0.50 어디에 두어도 `PEAK` 비율이 30~32% 로 같아, 실제 음악에서는 위치에 둔감합니다.

**검증 음원의 한계** — `test-03-buildup.wav` 의 `PEAK` 구간은 42초에 한 번 튄 뒤 0.45 대로 내려앉습니다. `PEAK` 최소 0.444 와 문턱 0.434 의 여유가 0.01 밖에 없습니다. 이 음원의 정점이 약하게 만들어진 탓이므로, 문턱을 다시 볼 일이 생기면 신스 음원이 아니라 실제 음악을 기준으로 삼으십시오.

#### BUILD 조건 (정량)

원래 명세의 "기울기가 양수이고 플럭스 평균이 상승 중"은 구현할 수 없는 문장이었고, **플럭스를 넣은 것 자체가 틀린 가정이었습니다.**

```
rmsSlope = 최근 3초 구간 전체의 최소제곱 회귀 기울기   (앞뒤 반쪽 평균 비교가 아님)

BUILD  ⟺  rmsSlope > 0.008 (초당)
```

조건은 이 하나뿐입니다.

#### 플럭스는 BUILD 판정에 쓰지 않습니다

`flux` 는 온셋의 양이라 **곡이 세지는 것이 아니라 음색이 바뀌는 것에 반응합니다.** 정점에서 새 악기가 들어오면 플럭스가 오르고, 빌드업 후반은 같은 소리가 커지기만 하므로 오히려 낮습니다.

`fluxRise = flux 최근 2초 평균 / 그 앞 2초 평균` 을 초당 기록해 보면 판별 방향이 반대입니다.

| 구간 | `fluxRise > 1.15` 통과 |
|---|---|
| BUILD (30~42초) | 4 / 12 |
| PEAK (42~50초) | **4 / 8** |

기울기가 가장 가파른 t=39~41 초(slope 0.010 → 0.046)에서 `fluxRise` 가 0.71~0.93 으로 탈락합니다. 빌드업의 한가운데를 막는 셈입니다.

문턱을 1.15 보다 낮추는 방법은 소용이 없습니다. `PEAK` 구간에서도 함께 통과하므로 판별력이 생기지 않습니다. **방향이 반대인 지표는 문턱을 어디에 두어도 두 구간을 가르지 못합니다.**

앞뒤 반쪽 평균을 비교하면 구간 안의 한 번의 튐에 휘둘립니다. 회귀는 구간 전체의 추세를 봅니다.

#### 전이 규칙 — 후보가 이어져야 채택합니다

"최소 1.2초 유지"를 **현재 상태를 붙잡는 것**으로 읽으면 깜빡임을 막지 못합니다. 1.2초가 지나는 순간의 값으로 상태가 정해지므로, 경계 근처에서는 1.2초마다 계속 뒤집힙니다.

**최근 1.2초 창에서 절반을 넘게 차지한 상태로 전환합니다.** 그리고 한 번 바뀌면 최소 1.2초를 유지합니다.

"1.2초 연속"이 아닙니다. 프레임 단위 판정 출력은 원래 지저분해서, 우세한 상태 사이사이에 다른 상태가 7~11% 섞여 나옵니다. 연속을 요구하면 그 한 프레임에 카운터가 되돌아가 `GROOVE` 가 93% 를 차지해도 1.2초를 못 채웁니다. 실측에서 상태가 첫 값에 35초간 눌러앉았습니다.

과반이 없으면 현재 상태를 유지합니다. 두 후보가 45 대 44 로 갈릴 때 억지로 바꾸지 않습니다.

최소 유지 시간을 함께 걸어야 합니다. 창 판정만으로는 전이 직후 0.8초 만에 또 바뀔 수 있습니다.

예외가 둘 있습니다.

| 상태 | 전이 방식 | 이유 |
|---|---|---|
| `SILENT` | **즉시 채택** | 조건 자체에 "0.5초 이상 지속"이 들어 있어 이미 흔들리지 않습니다 |
| `BREAK` | **즉시 채택 + 최소 0.8초 유지** | 음악이 뚝 끊긴 순간이 무대에서 가장 극적입니다. 1.2초 뒤에 화면이 반응하면 늦은 티가 납니다. 대신 다음 프레임에 곧바로 되돌아가지 않도록 최소 유지 시간을 겁니다 |
| 나머지 넷 | 1.2초 창에서 과반 + 최소 1.2초 유지 | |

`BREAK` 의 최소 유지가 끝나면 그때부터 1.2초 창 판정이 다시 작동합니다.

#### 무음 구간은 SILENT 입니다

드럼이 빠지고 패드만 남는 브레이크가 아니라 소리가 아예 없는 구간이면 `SILENT` 로 잡힙니다. 판정 순서상 `SILENT` 를 먼저 검사하기 때문이고, 규칙대로 동작한 것입니다. 검증 음원의 브레이크 구간이 완전 무음으로 만들어져 있으면 기대값을 `SILENT` 로 보십시오.

### 6-2. 결합 규칙

관객 에너지 `aud`(0~1)와 영향력 `infl`(0~1, 기본 0.6)이 있을 때, 실효 관객값을 이렇게 만듭니다.

```
audEff = aud × infl
```

`infl` 이 0 이면 `audEff` 가 0 이 되어 음악만으로 동작합니다. 관객 입력이 없거나 신뢰할 수 없을 때 안전하게 물러설 수 있어야 하므로 이 구조가 필요합니다.

결합의 기본 형태는 **곱이 아니라 가산 증폭**입니다.

```
final = base × (1 + audEff × gain)
```

곱으로 하면 관객이 조용할 때 화면이 꺼져 버립니다. 음악만으로도 기본 연출은 성립하고, 관객이 그 위에 얹히는 구조여야 합니다.

### 6-3. 파라미터 산출

각 파라미터마다 `base`(음악만)와 `gain`(관객 증폭 폭)을 정의합니다.

| 파라미터 | base | gain | 설명 |
|---|---|---|---|
| `density` | 상태별 기본값 × `(0.4 + rms × 0.6)` | 0.8 | 관객이 많이 반응할수록 요소가 늘어납니다 |
| `scale` | `0.3 + bands[LOW] × 0.7` | 0.5 | 저역과 관객이 함께 크기를 키웁니다 |
| `speed` | `bpm / 120` 를 0.5~2.0 로 제한 | 0.15 | 속도는 음악이 거의 결정합니다 |
| `brightness` | `0.25 + rms × 0.75` | 0.6 | |
| `hue` | 팔레트 `accent` 의 색상각 ÷ 360 (8절) | 0 | 색은 관객이 바꾸지 않습니다. 외부 연동 하위 호환용으로만 남깁니다 |
| `dreaminess` | `1 − arousal` (7-6절) | −0.35 | **음수 gain 입니다.** 객석이 뜨거울수록 몽환도가 내려가 화면이 날카로워집니다 |
| `expansion` | `0.1` | 1.5 | **관객이 주도하는 유일한 파라미터입니다** |
| `glitch` | `onsetPulse × 0.6 + 상태전이펄스 × 0.4` | 0.4 | |

상태별 `density` 기본값입니다.

| 상태 | 값 |
|---|---|
| SILENT | 0.05 |
| CALM | 0.25 |
| GROOVE | 0.50 |
| BUILD | 0.70 |
| PEAK | 0.95 |
| BREAK | 0.15 |

#### 관객 증폭을 검증할 때는 같은 음악 상태 안에서만 짝지어 재십시오

`DENSITY_BY_STATE` 가 0.05 / 0.15 / 0.50 처럼 계단으로 벌어져 있습니다. 그래서 관객 증폭을 재면서 상태를 섞어 놓으면, 두 조건의 **상태 분포 차이가 그대로 오차로 들어옵니다.** 관객이 무엇을 했는지가 아니라 그 구간에 어느 상태가 몇 번 들어왔는지를 재게 됩니다.

`glitch` 도 같은 이유로 흔들립니다. 기본값이 `onsetPulse × 0.6 + 상태전이펄스 × 0.4` 라 상태에 걸려 있고, 특히 `SILENT` 구간에서는 온셋도 전이도 없어 기본값이 0 으로 주저앉습니다. 그 구간 표본이 두 조건에 고르게 들어가지 않으면 비가 통째로 희석됩니다.

8단계 외부 연동(F-801)의 실측입니다. 관객 에너지 0.328, 예상은 `1 + 0.328 × gain` 입니다.

| 채널 | 섞어서 | ±SE | 같은 상태 안에서 | 예상 |
|---|---|---|---|---|
| `density` | 1.33 | **0.118** | 1.24 | 1.26 |
| `glitch` | 1.15 | **0.082** | 1.12 | 1.13 |
| `scale` | 1.15 | 0.026 | 1.15 | 1.16 |
| `brightness` | 1.16 | 0.043 | 1.16 | 1.20 |
| `expansion` | 1.49 | 0.054 | 1.49 | 1.49 |
| `dreaminess` | 0.86 | 0.023 | 0.86 | 0.89 |

SE 가 큰 둘이 정확히 `density` 와 `glitch` 입니다. 나머지 넷은 0.023~0.054 이고 상태를 갈라도 값이 움직이지 않습니다 — 기본값이 상태에 걸려 있지 않기 때문입니다.

`density` 를 상태별로 뜯으면 이렇습니다.

| 상태 | 0% | 100% | 배 | 표본 |
|---|---|---|---|---|
| BREAK | 0.081 | 0.104 | 1.28 | 289 / 286 |
| GROOVE | 0.312 | 0.397 | 1.27 | 36 / 44 |
| SILENT | 0.020 | 0.023 | 1.16 | 139 / 143 |
| 가중 평균 | | | **1.24** | |

`SILENT` 이 1.16 으로 낮은 것은 **결합식의 문제가 아닙니다.** 그 구간의 `density` 가 0.02 대인데 송출 채널이 소수 세 자리로 반올림하므로, 0.020 과 0.023 사이에 눈금이 세 칸밖에 없습니다. 반올림이 크게 먹는 자리입니다.

`glitch` 도 같은 방식으로 BREAK 1.12 · GROOVE 1.13 이 나오고, `SILENT` 은 0.000 → 0.002 라 비를 낼 수 없습니다.

색 관련 파라미터의 gain 을 0 으로 둔 것은 의도적입니다. 관객이 색까지 바꾸면 연출가가 정한 곡의 색채 계획이 무너집니다. 관객은 강도를 바꾸고 색은 음악이 정합니다. 팔레트 자체도 같은 이유로 관객 값을 받지 않습니다 (8-6절).

`expansion` 의 gain 이 1.5 로 가장 큰 이유는, 이 값이 관객의 존재를 화면에서 직접 드러내는 통로이기 때문입니다. 객석이 뜨거워지면 화면의 요소가 바깥으로 퍼져 나갑니다.

`dreaminess` 만 gain 이 음수입니다. 다른 파라미터는 관객이 뜨거울수록 값이 커지지만, 몽환도는 반대로 내려가야 합니다. 객석이 달아오른 순간에 화면이 더 흐릿하고 느려지면 어긋난 느낌을 줍니다. 계수를 0.35 로 억제한 것은, 관객이 아무리 뜨거워도 발라드가 댄스곡처럼 보이면 안 되기 때문입니다. 곡의 성격은 음악이 정하고 관객은 그 안에서 밀어 올릴 뿐입니다.

### 6-4. 구현 형태

이 결합은 한 함수에 모아야 합니다. 여기저기 흩어지면 나중에 어디서 합쳐지는지 찾을 수 없습니다.

```ts
// lib/direction/translate.ts
export function translate(
  music: MusicAnalysis,
  state: MusicState,
  audienceEnergy: number,
  influence: number,
  mood: Mood,                        // 7절에서 온 valence · arousal
  palette: ResolvedPalette,          // 8절에서 온, 보간이 끝난 색
  dreaminessLock: number | null,     // 오퍼레이터가 몽환도를 직접 고정한 경우
): DirectionParams {
  const audEff = audienceEnergy * influence;

  const amplify = (base: number, gain: number) =>
    clamp(base * (1 + audEff * gain), 0, 1);

  return {
    density:    amplify(DENSITY_BY_STATE[state] * (0.4 + music.rms * 0.6), 0.8),
    scale:      amplify(0.3 + music.bands[BAND.LOW] * 0.7, 0.5),
    speed:      clamp(music.bpm / 120, 0.5, 2.0) * (1 + audEff * 0.15),
    brightness: amplify(0.25 + music.rms * 0.75, 0.6),
    expansion:  amplify(0.1, 1.5),
    glitch:     amplify(music.onsetPulse * 0.6 + music.transitionPulse * 0.4, 0.4),

    // 분위기에서 오는 값 (7절)
    dreaminess: dreaminessLock ?? amplify(1 - mood.arousal, -0.35),
    mood,                                  // valence · arousal · 이름
    palette,                               // 보간이 끝난 색 다섯 (8절)
    hue:        hueOf(palette.accent),     // 외부 연동 하위 호환

    // 화면에 두 층으로 그리기 위해 음악만의 값도 함께 반환합니다
    _musicOnly: { /* audEff 를 0 으로 두고 계산한 같은 값들 */ },
  };
}
```

`_musicOnly` 를 함께 반환하는 이유는 `03-screens.md` 의 08 패널에서 두 층을 겹쳐 그리기 위해서입니다. 관객이 기여한 몫이 화면에 보여야 이 프로젝트가 무엇을 하는지 설명할 수 있습니다.

## 7. 분위기 판정 — 곡의 성격을 두 실수로

**이 절은 이번에 새로 넣은 것입니다.** 앞의 6절이 "지금 이 순간이 얼마나 센가"를 판정한다면, 이 절은 "이 곡이 어떤 성격인가"를 판정합니다. 발라드에서 몽환적인 화면이 나오고 댄스곡에서 강렬한 화면이 나오려면 순간 상태만으로는 부족합니다. 순간 상태는 후렴마다 `PEAK` 로 올라가는데, 발라드의 후렴과 댄스곡의 후렴은 같은 화면이면 안 되기 때문입니다.

두 축을 씁니다.

| 축 | 뜻 | 무엇을 정하는가 |
|---|---|---|
| `valence` | 밝음 ↔ 어두움 (0~1) | **색** — 어떤 팔레트를 쓸지 |
| `arousal` | 격렬함 ↔ 잔잔함 (0~1) | **결** — 화면이 몽환적일지 날카로울지 |

이 두 줄이 이번 확장의 전부입니다. 색은 밝기에서 오고, 결은 격렬함에서 옵니다.

### 7-1. 크로마 12빈

지금까지 후순위로 미뤄 두었던 것을 여기서 씁니다. 장조인지 단조인지를 근사해야 곡이 밝은지 어두운지를 판단할 수 있습니다.

주파수 빈을 12개 음높이 계급으로 접습니다.

```
midi = 69 + 12 × log2(f / 440)
pc   = round(midi) mod 12
chroma[pc] += mag[i]
```

- 대역을 100~2000Hz 로 제한합니다. 그 아래는 킥이 모든 계급에 새고, 그 위는 배음이 원래 음높이를 가립니다
- 프레임마다 합이 1 이 되도록 정규화합니다
- **지수 평활 계수 0.90 을 겁니다.** 화음은 마디 단위로 바뀌므로 프레임마다 흔들리면 안 됩니다. 시상수로 약 1.5초입니다
- 8프레임에 한 번만 계산해도 충분합니다. 매 프레임 돌릴 이유가 없습니다

### 7-2. 장조·단조 근사

크로마 벡터를 Krumhansl-Schmuckler 프로파일과 상관시킵니다. 12개 조성 × 장단 2 = 24개 중 상관이 가장 큰 것을 고릅니다.

```
major = [6.35, 2.23, 3.48, 2.33, 4.38, 4.09, 2.52, 5.19, 2.39, 3.66, 2.29, 2.88]
minor = [6.33, 2.68, 3.52, 5.38, 2.60, 3.53, 2.54, 4.75, 3.98, 2.69, 3.34, 3.17]

majorness = clamp((최고 장조 상관 − 최고 단조 상관) × 2.5 + 0.5, 0, 1)
chromaConf = 최고 상관값                      // 0~1, 화음이 뚜렷할수록 높습니다
```

곱셈 288회짜리 계산이라 비용은 무시할 만합니다.

이 방법이 완벽하지는 않습니다. 무조 음악이나 드럼만 나오는 구간에서는 값이 흔들립니다. 그래서 `chromaConf` 를 함께 내보내고, 신뢰도가 낮으면 `valence` 에서 이 항의 비중을 줄입니다.

### 7-3. valence — 밝음

```
valence = clamp(
    0.50 × majorness × chromaWeight
  + 0.28 × norm(centroid, 300, 3500)
  + 0.12 × norm(bands[AIR], 0, 0.60)
  + 0.10 × (1 − norm(bands[SUB], 0, 0.70))
, 0, 1)

chromaWeight = clamp(chromaConf / 0.55, 0, 1)
```

`chromaWeight` 로 비중을 줄일 때 남는 몫은 나머지 세 항에 비례 배분합니다. 화음을 못 읽는 구간에서 무조건 어둡게 판정하면 안 되기 때문입니다.

**시상수 6초로 평활합니다.** 곡 안에서 색이 자주 바뀌면 무대가 산만해집니다. 한 곡의 색은 대체로 하나여야 하고, 바뀌더라도 관객이 알아채지 못할 만큼 천천히 바뀌어야 합니다.

### 7-4. arousal — 격렬함

```
arousal = clamp(
    0.34 × rms6s                                  // 6초 이동평균
  + 0.24 × norm(bpm, 60, 150) × bpmWeight
  + 0.24 × norm(onsetRate, 0, 6)                  // 최근 4초의 초당 온셋 수
  + 0.18 × norm(bands[HI], 0, 0.55)
, 0, 1)

bpmWeight = clamp(bpmConf / 0.45, 0, 1)
```

BPM 신뢰도가 0 이면 그 항을 빼고 남은 가중치를 나머지에 비례 배분합니다. 근거 없는 BPM 을 그대로 넣으면 곡 시작 몇 초 동안 분위기가 튑니다.

**시상수 3초로 평활합니다.** `valence` 보다 빠르게 반응해야 합니다. 후렴에 들어가면 화면이 세져야 하고, 그 반응이 6초 늦으면 후렴이 끝난 뒤에 세집니다.

### 7-5. 분위기 다섯 이름

두 축의 평면을 다섯 구역으로 나눕니다.

| 이름 | 표시 | 조건 | 어떤 곡인가 |
|---|---|---|---|
| `DEEP` | 침잠 | `arousal < 0.38`, `valence < 0.50` | 어둡고 느린 곡, 단조 발라드 |
| `SERENE` | 평온 | `arousal < 0.38`, `valence ≥ 0.50` | 밝고 잔잔한 곡, 어쿠스틱 |
| `FERVENT` | 격정 | `arousal ≥ 0.62`, `valence < 0.55` | 어둡고 센 곡, 록·하드 일렉트로닉 |
| `RADIANT` | 희망 | `arousal ≥ 0.62`, `valence ≥ 0.55` | 밝고 신나는 곡, 댄스·팝 |
| `NEUTRAL` | 중립 | 나머지 | 중간 지대 |

경계에서 이름이 왔다 갔다 하지 않도록 두 장치를 겁니다.

- 한 번 판정한 이름은 **최소 8초 유지**합니다
- 경계를 넘을 때 0.06 의 여유를 둡니다. 나갈 때의 경계가 들어올 때보다 멀리 있습니다

**이름은 표시용입니다. 실제 연출은 `(valence, arousal)` 두 실수를 직접 씁니다.** 이름으로 분기해서 화면을 만들면 경계를 넘는 순간 화면이 끊깁니다. 다섯 이름은 팔레트 자동 선택의 앵커와 화면에 글자로 띄우는 용도로만 씁니다.

### 7-6. dreaminess — 몽환도

`arousal` 을 뒤집은 값입니다. 무대 씬이 이 값 하나로 결을 바꿉니다.

```
dreaminessBase = 1 − arousal
dreaminess     = clamp(dreaminessBase × (1 − audEff × 0.35), 0, 1)
```

0 이면 날카롭고 빠른 화면, 1 이면 번지고 느린 화면입니다. 어느 자리에 어떻게 들어가는지는 `03-screens.md` 의 무대 씬 절에 표로 있습니다.

**오퍼레이터가 직접 고정할 수 있습니다.** 리허설에서 "이 곡은 자동 판정보다 더 몽환적으로 가자"고 정하면 그 값을 프리셋에 저장합니다 (`06-data-model.md` 의 `dreaminess_lock`). 고정하면 자동 판정을 무시합니다.

## 8. 팔레트 — 색을 정하는 규칙

원본 프로토타입은 `mono` · `alert` · `duo` 세 톤뿐이었고, 실제 색은 흰색에 빨강이나 청록을 얹는 수준이었습니다. 이번 확장에서는 색을 팔레트 단위로 다루고, 분위기가 팔레트를 자동으로 고르게 합니다.

### 8-1. 팔레트 구조

한 팔레트는 역할 다섯 개의 색으로 이루어집니다.

| 역할 | 쓰이는 곳 |
|---|---|
| `bg` | 무대 배경의 가장 어두운 자리. 완전한 검정이 아니라 색조를 아주 옅게 머금습니다 |
| `deep` | 배경 유체의 어두운 층 |
| `base` | 입자와 실의 기본색 |
| `accent` | 강조. 가사의 현재 단어, 세로실, 밝은 입자 |
| `hot` | 비트가 오는 순간에만 짧게 나타나는 색 |

씬은 색을 직접 쓰지 않고 이 다섯 역할로만 그립니다. 그래야 팔레트를 갈아 끼워도 씬 코드를 고칠 일이 없습니다.

### 8-2. 기본 팔레트 여덟

| 이름 | 표시 | `bg` | `deep` | `base` | `accent` | `hot` |
|---|---|---|---|---|---|---|
| `DEEP` | 침잠 | `#01040E` | `#0A1740` | `#3B5BD9` | `#6E86F0` | `#C3D0FF` |
| `SERENE` | 평온 | `#03080C` | `#0B2430` | `#7FD7D0` | `#A8E6DF` | `#E8FBF7` |
| `RADIANT` | 희망 | `#0B0703` | `#3A2405` | `#FFC53D` | `#FFE27A` | `#FFF6D6` |
| `FERVENT` | 격정 | `#0A0204` | `#3B0512` | `#FF2A00` | `#FF6B8A` | `#FFD1DA` |
| `MONO` | **MONO** (기본값) | `#000000` | `#14140F` | `#E8E4DC` | `#7FD7D0` | `#FF2A00` |
| `ABYSS` | 심해 | `#00070A` | `#052430` | `#0FA3A3` | `#55E0C8` | `#EAFFFA` |
| `EMBER` | 노을 | `#0C0403` | `#40120A` | `#FF7A2F` | `#FFB35C` | `#FFE7C4` |
| `FROST` | 설야 | `#04060A` | `#131A24` | `#DCE6F2` | `#8FB6E8` | `#FFFFFF` |

앞의 넷이 자동 선택의 기본 후보입니다. **`MONO` 를 포함한 나머지 넷은 기본이 수동 선택용(`auto: false`)입니다.** 이유는 8-3절에 있습니다.

기본 앵커 좌표는 이렇습니다. 수동 선택용에도 좌표를 주는 것은, 사용자가 자동 후보로 켰을 때 한자리에 겹치지 않게 하기 위해서입니다.

| 팔레트 | valence | arousal | 기본 자동 후보 |
|---|---|---|---|
| 침잠 | 0.22 | 0.20 | 예 |
| 평온 | 0.72 | 0.20 | 예 |
| 격정 | 0.20 | 0.82 | 예 |
| 희망 | 0.80 | 0.82 | 예 |
| MONO | 0.50 | 0.50 | **아니요** |
| 심해 | 0.35 | 0.35 | 아니요 |
| 노을 | 0.65 | 0.55 | 아니요 |
| 설야 | 0.60 | 0.30 | 아니요 |

`MONO` 는 기존 시각 언어(`03-screens.md` 2절)의 색 그대로입니다. 원본의 `mono` 톤이 여기로 흡수됩니다. `FERVENT` 가 원본의 `alert`, `SERENE` 이 `duo` 에 해당합니다.

**분위기 이름과 팔레트 이름은 별개입니다.** 7-5절의 분위기 `중립 NEUTRAL` 은 두 축 평면의 한가운데 구역을 가리키는 이름이고, 여기 팔레트 `MONO` 는 무채색 기본 톤입니다. 둘은 짝이 아니며, 분위기가 `중립` 이라고 `MONO` 팔레트가 뽑히지 않습니다.

분위기 `중립` 구역에 대응하는 팔레트는 없습니다. 그 구역의 곡은 네 모서리 중 가까운 둘이 섞입니다 (8-3절).

### 8-3. 자동 선택 — 앵커와 역거리 가중

각 팔레트에 `(valence, arousal)` 평면의 앵커 좌표를 줍니다 (8-2절 표).

현재 분위기 점에서 가장 가까운 앵커 **두 개**를 골라 역거리로 섞습니다. 하나만 고르면 경계에서 색이 툭 바뀝니다.

#### MONO 는 자동 후보에서 뺍니다

`MONO` 의 앵커가 평면 한가운데(0.50, 0.50)에 있고 `base` 가 무채색 뼈색이라, **거의 모든 곡에서 두 번째로 가까운 앵커가 되면서 색을 바래게 만듭니다.**

실측에서 확인된 문제입니다. `test-09-mood-radiant.wav` 는 분위기가 `희망` 으로 옳게 판정됐는데, 섞임이 `MONO 53% + 희망 47%` 로 나와 무대색이 `#6a5f4a` 라는 탁한 갈색빛이 됐습니다. 노랑이 아닙니다.

```
판정점 (0.58, 0.70)
  → 희망 앵커(0.80, 0.82) 까지 0.251
  → MONO 앵커(0.50, 0.50) 까지 0.215     ← 더 가깝다
```

MONO 를 후보에서 빼면 두 번째가 `격정` 이 되어 `희망 61% + 격정 39%`, 주황빛 노랑이 나옵니다. 곡의 성격에 맞는 색입니다.

MONO 는 수동 선택용으로 남깁니다. 원본 프로토타입의 `mono` 톤을 재현할 때 씁니다.

**중간 지대 곡은 네 모서리 중 가까운 둘이 섞습니다.** 평면 한가운데(0.50, 0.50)라면 `평온 53% + 침잠 47%` 로 청록빛 파랑이 됩니다. 회색보다 무대에 걸 만합니다.

```
d1, d2 = 가까운 두 앵커까지의 거리
w1 = d2 / (d1 + d2),  w2 = 1 − w1
target[role] = oklabMix(p1[role], p2[role], w2)
```

**색은 OKLab 공간에서 섞습니다.** sRGB 값을 그대로 선형 보간하면 파랑과 노랑 사이가 탁한 회색을 지나갑니다. OKLab 에서 섞으면 중간이 초록 계열로 지나가 눈에 자연스럽습니다.

```
// sRGB(감마 제거된 선형값) → OKLab
l = 0.4122214708r + 0.5363325363g + 0.0514459929b
m = 0.2119034982r + 0.6806995451g + 0.1073969566b
s = 0.0883024619r + 0.2817188376g + 0.6299787005b
L = 0.2104542553·l⅓ + 0.7936177850·m⅓ − 0.0040720468·s⅓
a = 1.9779984951·l⅓ − 2.4285922050·m⅓ + 0.4505937099·s⅓
b = 0.0259040371·l⅓ + 0.7827717662·m⅓ − 0.8086757660·s⅓
```

역변환 계수는 `lib/palette/oklab.ts` 에 함께 둡니다.

### 8-4. 전환은 천천히

목표 팔레트가 바뀌어도 화면 색을 즉시 갈지 않습니다. **시상수 2.5초로 따라갑니다** (사용자가 0.5~8초로 조절 가능). 공연 중에 색이 한 프레임에 바뀌면 조명 사고처럼 보입니다.

```
current[role] = oklabMix(current[role], target[role], 1 − exp(−dt / fade))
```

**새 파일을 로드해도 보간기를 비우지 않습니다.** 곡이 바뀌는 순간이야말로 색이 크게 움직이는 자리인데, 여기서 보간기를 초기화하면 새 목표색이 한 프레임에 그대로 찍힙니다. 이 절이 막으려는 장면이 정확히 그것입니다. 분위기 판정(`valence` · `arousal` 누적)은 비우고, 색 보간기만 이어 갑니다.

**컬러칩을 편집하는 중에도 이 시상수를 지킵니다.** `03-screens.md` 의 "즉시 반영"은 "저장 버튼을 기다리지 않는다"는 뜻이지 "한 프레임에 바꾼다"는 뜻이 아닙니다. 시상수 2.5초에서도 첫 0.25초에 11% 가 움직이므로 편집자에게는 즉시 반응하는 것으로 보입니다.

### 8-4-2. 기본 팔레트를 고치면

기본 제공 여덟은 지울 수 없고, 고치면 사본이 만들어집니다. 그때 **사본이 원본의 `auto` 를 물려받고 원본은 자동 후보에서 빠집니다.**

원본을 후보에 남겨 두면 앵커를 끌어 옮겼을 때 원본이 제자리에 남아 후보가 둘이 되고, "앵커를 옮기면 다른 팔레트가 뽑힌다"가 성립하지 않습니다.

### 8-5. 자동과 수동은 둘 중 하나입니다

**섞지 않습니다.** 자동이 켜져 있으면 분위기가 색을 온전히 정하고, 꺼져 있으면 고른 팔레트 하나만 씁니다.

```
자동 켬  →  final[role] = auto[role]       // 8-3절의 두 앵커 혼합
자동 끔  →  final[role] = selected[role]   // 고른 팔레트 그대로
```

#### 카드를 누르면 자동이 꺼집니다

`03-screens.md` 의 `F-303-2` 가 쓰는 원칙과 같습니다. **사람이 개입하면 자동이 물러납니다.** 팔레트 카드를 누른다는 것 자체가 "내가 색을 정하겠다"는 의사이므로 그대로 존중합니다.

| 조작 | 결과 |
|---|---|
| 자동이 켜진 상태 | **어느 카드에도 선택 표시가 없습니다.** 섞임 표시로 지금 무엇이 섞이는지만 보여 줍니다 |
| 카드를 누름 | 자동이 꺼지고 그 카드가 선택됩니다 |
| `자동` 을 다시 켬 | 선택이 풀립니다 |
| `자동` 을 토글로 끔 (카드를 안 누르고) | **직전 섞임에서 우세했던 팔레트**가 선택됩니다. 색이 크게 튀지 않고, 카드 하나가 실제로 선택된 상태가 됩니다 |

어느 경우든 색은 8-4절의 시상수를 지나 넘어갑니다.

**자동이 켜진 동안 선택 표시를 두지 않는 것이 핵심입니다.** 표시가 있으면 오퍼레이터가 그 색이 지금 나가는 색이라고 오해합니다. 자동일 때 "지금 나가는 색"은 카드 하나가 아니라 둘의 혼합이고, 그것은 섞임 표시가 이미 말해 줍니다.

#### 색 추종 강도는 없앴습니다

이전 명세에는 선택 팔레트와 자동 팔레트를 `follow` 비율로 섞는 슬라이더가 있었습니다. 두 가지 이유로 뺍니다.

- **색을 바래게만 했습니다.** 선택 팔레트의 기본값이 `MONO` 이고 그 `base` 가 무채색이라, 100% 아래로 내리면 무채색이 그만큼 섞여 채도가 깎였습니다. 실측에서 80% 일 때 밝은 곡의 노랑이 무뎌졌습니다
- **자동과 수동이 배타가 되면 섞을 대상이 없습니다.** 자동일 때 선택 팔레트가 아예 없습니다

"이 곡은 이 색으로 간다"는 필요는 프리셋(`F-701`)이 채웁니다. 곡마다 팔레트와 자동 여부를 저장해 두면 로드할 때 그대로 복원됩니다.

### 8-6. 색이 맞는지 재는 방법

**캔버스 평균으로 판정하지 마십시오.** 씬이 색을 어떻게 칠하느냐에 따라 평균이 크게 왜곡됩니다.

직조 씬에서 실측한 예입니다. 팔레트의 `base` 는 `#ffa22f`(색상각 33°, 채도 82%)로 밝은 주황인데, 같은 화면의 캔버스 평균은 `#6c5640`(30°, 41%)으로 나왔습니다. 어두운 갈색처럼 보입니다.

직조는 `base` 를 투명도 `0.10 + v × 0.90` 의 가는 실로 검은 바탕 위에 긋습니다. **화면 대부분이 빈 바탕이라 평균이 검정 쪽으로 끌려갑니다.** 색상각은 살아남고 채도와 명도만 깎입니다. 무대 씬은 가산 블렌딩이라 반대 방향으로 왜곡됩니다.

색이 맞는지는 이렇게 봅니다.

| 재는 것 | 방법 |
|---|---|
| 팔레트가 옳게 뽑혔는가 | 역할 다섯의 HEX 를 직접 찍어 색상각·채도를 본다 |
| 섞임이 옳은가 | 섞임 표시의 이름과 비율 |
| 화면이 그 색으로 보이는가 | 눈으로. 굳이 수치화하려면 **밝은 픽셀 상위 10%** 의 평균을 쓴다 |

마지막 줄이 실용적입니다. 밝은 10% 의 평균은 실측에서 `#e68c29`(31°, 82%)로 `base` 와 사실상 같게 나왔습니다.

### 8-7. 관객은 색을 바꾸지 않습니다

6-3절의 원칙을 그대로 지킵니다. 관객 에너지는 팔레트 선택에도, 색 보간에도 들어가지 않습니다. 관객이 색까지 바꾸면 연출가가 곡마다 잡아 둔 색채 계획이 무너집니다.

## 9. 아직 넣지 않은 것

**노벨티 곡선** — 음색과 에너지의 급변 지점을 찾아 곡의 구간 전환을 감지하는 방법입니다. 지금은 상태 판정을 RMS 와 플럭스로만 하고 있어서, 후렴 진입 같은 구조적 전환을 놓칩니다. 자기유사도 행렬을 쓰면 정확하지만 무겁습니다. 최근 N 프레임의 스펙트럼 평균과 현재 스펙트럼의 코사인 거리로 가볍게 근사하는 방법을 먼저 시도해 보시기 바랍니다.

이것이 들어오면 `arousal` 의 반응이 빨라지고, 후렴 진입에서 팔레트가 한 박 먼저 움직일 수 있습니다. 다만 없어도 지금 구조는 성립합니다.
