# 07. 개발 로드맵

각 단계는 그 자체로 실행되고 확인 가능한 상태로 끝납니다. 다음 단계를 시작하기 전에 완료 기준을 눈으로 확인하시기 바랍니다.

---

## 1단계 — 뼈대와 오디오 입력

**목표**: 음원을 재생하고 RMS 가 움직이는 것을 확인합니다.

- Next.js 프로젝트 생성, TypeScript, Tailwind, App Router
- `lib/types.ts` 에 타입 정의 (`06-data-model.md` 4절)
- 콘솔 레이아웃 뼈대: 상단 바, 좌우 레일, 중앙 무대, 하단 트랜스포트
- 디자인 토큰을 CSS 변수로 (`03-screens.md` 2절)
- `lib/audio/engine.ts`: AudioContext 생성, 파일 로드와 디코딩, 재생·정지
- `lib/audio/engine.ts`: 라인/마이크 입력 (F-102). **이 항목은 v40 에서 추가했습니다.** 처음 로드맵에 F-103 만 넣고 F-102 를 빠뜨려, 여덟 단계가 끝나도록 구현되지 않았습니다 (`issues/21`)
- AnalyserNode 두 개 연결, RMS 만 계산해 상단 바에 표시

**완료 기준**: MP3 를 끌어다 놓고 재생하면 상단 바의 RMS 숫자가 음악에 맞춰 움직입니다.

---

## 2단계 — 음악 분석 완성

**목표**: BPM 과 비트가 잡힙니다. 이 단계가 이 프로젝트에서 기술적으로 가장 까다롭습니다.

- 스펙트럴 플럭스, 6밴드, 센트로이드 (`05-signal-processing.md` 2절)
- 온셋 검출 (3-1절). 적응 임계값을 그대로 구현합니다
- 온셋 엔벨로프 100Hz 버퍼 (3-2절)
- BPM 추정: 자기상관 + 빗살 점수 + 템포 연속성 (3-3절)
- 비트 트래킹과 위상 스냅 (3-4절)
- 스템 추정 (4절)
- 09 분석 리드아웃 패널에 모든 값 표시
- 데모 신스 구현 (F-103)

**완료 기준**: 데모 신스를 켜면 BPM 이 120 근처로 수렴하고, 실제 음원 세 곡에서 귀로 듣는 박자와 화면의 비트가 어긋나지 않습니다.

**주의**: 이 단계를 대충 넘기면 이후 모든 연출이 흔들립니다. 곡을 여러 개 걸어 보고 BPM 이 절반이나 두 배로 잡히지 않는지 확인하시기 바랍니다. 빗살 점수와 옥타브 접기가 바로 그 문제를 막는 장치입니다.

## 3단계 — 첫 씬과 출력 창

**목표**: 음악이 화면을 움직입니다.

- `components/stage/Stage.tsx`: 캔버스 컨테이너, `devicePixelRatio` 반영, 리사이즈 대응
- 직조 씬 구현 (`03-screens.md` 4절)
- 스펙트럼 씬 구현 (진단용이라 먼저 만들면 편합니다)
- 잔상·입자 효과
- 출력 창 분리 (F-506). `window.open` 과 `BroadcastChannel` 로 상태를 전달합니다
- 단축키 (1~6, Space, B, O, F, P)

**완료 기준**: 재생하면 직조 씬에 줄이 비트마다 쌓이고, 출력 창을 두 번째 화면으로 옮겨도 같이 움직입니다. 60fps 를 유지합니다.

## 4단계 — 관객 입력

**목표**: 관객 에너지가 0~1 로 나옵니다.

- `lib/audience/types.ts` 에 `AudienceSource` 인터페이스
- 시뮬레이션 구현 (F-303). 카메라 없이 개발할 수 있어야 하므로 이것부터 만듭니다
- 카메라 방식 구현 (F-301, `05-signal-processing.md` 5-1절)
- 자동 보정 (5-3절)과 어택·릴리스 평활 (5-4절)
- 04 관객 패널 전체 (`03-screens.md` 3절)
- 관객 씬 구현

**완료 기준**: 카메라 앞에서 움직이면 값이 오르고, 조명을 껐다 켜도 급등하지 않습니다. 20초 뒤 보정 완료가 뜹니다.

## 5단계 — 연출 번역 ★

**목표**: 두 신호가 합쳐집니다. **이 단계가 프로젝트의 이유입니다.**

**5-A. 결합**

- `lib/direction/state.ts`: 음악 상태 판정 (`05-signal-processing.md` 6-1절)
- `lib/direction/translate.ts`: 결합 규칙과 파라미터 산출 (6-2, 6-3절)
- 08 연출 파라미터 패널: 두 층 막대로 관객 기여분을 시각화
- 관객 영향력 슬라이더 (F-403)
- 모든 씬이 `DirectionParams` 를 읽어 그리도록 개편

**5-B. 분위기와 색**

- `lib/audio/chroma.ts`: 크로마 12빈과 장·단 근사 (7-1, 7-2절)
- `lib/direction/mood.ts`: `valence` · `arousal` 판정 (7-3~7-5절)
- 몽환도 산출 (7-6절)
- `lib/palette/`: 기본 팔레트 여덟, OKLab 보간, 분위기 자동 선택 (8절)
- 05 팔레트 패널: 컬러칩 편집, 자동 스위치, 분위기 2축 평면
- 기존 씬들이 팔레트의 역할 다섯 개로 색을 내도록 개편

**완료 기준**: 다섯 가지를 확인합니다.
1. 관객 영향력을 0 으로 내리면 관객이 움직여도 화면이 변하지 않습니다
2. 100 으로 올리고 관객 에너지를 올리면 화면이 눈에 띄게 강해집니다
3. 관객 입력을 아예 꺼도 음악 연출은 그대로 동작합니다
4. 발라드와 댄스곡을 번갈아 걸면 `arousal` 이 뚜렷하게 갈리고, 자동 팔레트가 서로 다른 색을 고릅니다
5. 자동을 끄고 컬러칩을 직접 고치면 그 색이 즉시 화면에 나옵니다

3번이 특히 중요합니다. 공연 현장에서 카메라가 말썽을 부려도 무대는 계속 가야 합니다.

## 6단계 — 무대 씬과 가사

**목표**: 무대에 걸 화면이 나옵니다. 여기까지 오면 이 프로젝트를 남에게 보여 줄 수 있습니다.

**6-A. 무대 씬 (F-507)**

- WebGL2 컨텍스트와 셰이더 파이프라인 (`03-screens.md` 무대 씬 절)
- 층 1 배경 유체 — 도메인 워핑 노이즈
- 층 2 입자 — 상태 없는 절차적 위치, 비트 확산
- 층 3 블룸 — 1/4 해상도 블러 두 번, 가산 합성
- 몽환도가 열 자리에 들어가는 것 확인 (표 그대로)
- 07 씬 파라미터 패널 (F-508)

**6-B. 가사 큐와 합성 씬**

- LRC 파싱과 가사 큐 (F-601, F-602)
- 가사 씬, 합성 씬
- 구간 반복 (F-202)

합성 씬에 관객 격자를 겹치지 않습니다. 바탕이 되는 무대 씬이 관객 값을 이미 받고 있어서, 격자를 한 겹 더 얹으면 같은 값이 두 번 들어갑니다.

**6-C. LRC 편집기**

- 직접 입력, 균등 배분, 줄 목록 편집, 전체 오프셋 (F-603)
- 탭 모드와 배너 (F-604)
- `LRC 내보내기` (F-605 앞부분)

**Supabase 저장은 7단계로 넘겼습니다.** 이 단계에는 Supabase 연결이 아직 없어서, 저장까지 여기서 하면 스키마와 RLS 가 7단계보다 먼저 끌려 들어옵니다. 만든 큐는 `.lrc` 로 내려받아 두었다가 다시 올려서 씁니다.

**완료 기준**:
1. 잔잔한 곡과 신나는 곡의 무대 화면이 서로 다른 곡의 것으로 보입니다
2. 비트마다 입자가 바깥으로 퍼집니다
3. 1920×1080 출력 창에서 60fps 를 유지합니다
4. 합성 씬에서 바탕과 가사가 서로 가리지 않고, 관객 격자가 그려지지 않습니다
5. 가사가 음악과 맞게 넘어가고, 탭 모드로 찍은 타임스탬프가 그대로 재생됩니다
6. 탭 모드를 끄면 `Space` 가 다시 재생과 일시정지로 돌아옵니다
7. 내보낸 `.lrc` 를 다시 올리면 같은 큐가 됩니다

## 8단계 — 외부 연동

**원본 프로토타입에 이미 있는 기능을 옮기는 단계입니다.** `resona.html` 의 「08 · TouchDesigner 라우팅」 패널이 WebSocket 연결·형식 전환·송출 레이트·채널 표·연동 스니펫을 모두 갖추고 있습니다. 새로 설계하지 말고 그 구현을 가져오되, 세 자리를 바꿉니다.

- WebSocket 송출 (F-801). 송출 주기는 기본 60, 슬라이더 5~120
- **자동 재연결** — 원본에 없습니다. 1초에서 시작해 두 배씩, 최대 10초
- **채널 표를 새로 짭니다** (F-802). 원본의 `face/count` · `face/max` 대신 정규화된 관객 에너지와 `DirectionParams` · 분위기 · 팔레트를 내보냅니다
- **가사 채널은 `lyric/ordinal`** 로 바꿉니다. 시각 미정 줄이 섞이면 배열 번호와 어긋납니다
- TouchDesigner 콜백 스크립트 제공 (F-803). 문자열 채널을 Table DAT 으로 갈라 받게 갱신합니다
- HTTPS 제약 안내 문구

**완료 기준**: 로컬 실행 상태에서 WebSocket 수신 도구로 값이 들어오고, 관객 영향력을 움직이면 `/resona/dir/*` 가 따라 움직입니다. 상대 쪽을 껐다 켜면 사람 손 없이 `LIVE` 로 돌아옵니다.

**왜 채널을 바꾸는가**: 얼굴 수를 그대로 내보내면 받는 쪽이 연출을 다시 계산하게 됩니다. 음악이 무엇을 연출할지 정하고 관객이 그것을 얼마나 강하게 할지 정한다는 이 프로젝트의 결합 규칙은 `translate.ts` 한 곳에만 있어야 합니다. 그 원칙이 무대 밖에서 깨지지 않게 합니다.

**배포본에서는 쓰지 못합니다.** https 페이지에서 `ws://` 로 나가는 것을 브라우저가 막습니다. 이 단계의 확인은 전부 로컬 실행에서 합니다.

## 이후 과제

여덟 단계가 끝난 뒤의 몫입니다. 각각 `issues/16` ~ `issues/20` 에 목표·작업·완료 기준을 적어 두었습니다. 앞 단계들과 달리 **답이 정해져 있지 않은 자리**입니다. 근사식을 고르고 임계값을 화면 보며 정하는 일이라, 정한 값을 명세에 되돌려 적는 것까지가 한 과제입니다.

| 이슈 | 과제 | 원본에 있었는가 |
|---|---|---|
| 16 | 마이크 방식 관객 입력 (F-302) | 없음. 관객 입력은 카메라 하나뿐이었습니다 |
| 17 | 노벨티 곡선으로 구간 전환 감지 | 없음 |
| 18 | 세션 기록과 되돌아보기 (F-901 · F-902) | 없음 |
| 19 | 4트랙 스템 파일 로드 (F-104) | **있음.** 옮기지 않은 것입니다 |
| 20 | 나머지 씬의 WebGL 이전 | 원본은 전부 Canvas 2D 입니다 |

**19 는 성격이 다릅니다.** 나머지 넷은 원본에도 없던 신규 설계이지만, 4트랙 스템 로드는 원본 `resona.html` 에 `loadStemFile()` 로 이미 동작하고 있습니다. 새로 설계하지 말고 옮기십시오.

**착수 순서는 로드맵 순서와 다를 수 있습니다.** 위 표는 「실제 공연장에서 쓸 수 있는가」 기준의 우선순위입니다. 남은 시간이 짧다면 18(테이블이 이미 있어 가장 쌉니다)이나 17(화면에서 가장 잘 보입니다)부터 잡는 편이 낫습니다.

**20 은 프레임이 실제로 모자랄 때만 엽니다.** 지금 60fps 가 나오고 있다면 손대지 마십시오.

크로마 특징은 이 목록에서 빠졌습니다. 색상 자동 결정에 필요해져 5단계로 올라갔습니다.

## 개발 중 지켜야 할 것

**매 단계 끝에 실제로 소리를 틀어 확인합니다.** 이 프로젝트는 수치가 맞는지보다 화면이 음악과 맞아 보이는지가 중요합니다. 단위 테스트로는 판단할 수 없습니다.

**파라미터를 임의로 바꾸지 않습니다.** `05-signal-processing.md` 의 숫자와 직조 씬의 격자 값은 기존 프로토타입에서 실제로 동작하던 값입니다. 바꿔야 한다면 왜 바꾸는지 기록을 남기시기 바랍니다.

**무대 씬의 숫자는 예외입니다.** 이번에 새로 설계한 것이라 근거가 되는 실행 기록이 없습니다. 화면을 보고 조정하시되, 조정한 값을 `03-screens.md` 에 되돌려 적어 다음 사람이 같은 자리에서 출발하게 하십시오.

**관객이 없어도 동작하는지 항상 확인합니다.** 관객 입력을 붙인 뒤로는 그것 없이 실행해 보는 일이 줄어듭니다. 단계마다 한 번씩 꺼 보시기 바랍니다.

**프레임 예산을 지킵니다.** 새 기능을 붙일 때마다 fps 를 확인하고, 30 아래로 떨어지면 그 자리에서 해결합니다. 나중으로 미루면 어느 것이 원인인지 찾기 어려워집니다.
