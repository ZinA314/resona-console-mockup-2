# 04. 서비스 흐름

## 1. 데이터 흐름 전체 그림

```
 ┌── 음악 입력 ──────────┐        ┌── 관객 입력 ──────────┐
 │ 파일 · 마이크 · 데모   │        │ 카메라 · 마이크 · 시뮬 │
 └──────────┬───────────┘        └──────────┬───────────┘
            │                                │
   AudioWorklet 분석                  모션/음향 측정
   (오디오 스레드)                      (30fps)
            │                                │
   ┌────────▼────────┐              ┌────────▼────────┐
   │  MusicAnalysis  │              │ audienceEnergy  │
   │  온셋·BPM·비트    │              │    0.00~1.00    │
   │  6밴드·RMS·센트로  │              │   (자동 보정됨)   │
   │  스템 4종         │              └────────┬────────┘
   └────────┬────────┘                       │
            │                                │
            └──────────┬─────────────────────┘
                       │
            ┌──────────▼──────────┐
            │   연출 번역 엔진      │   ← 이 프로젝트의 핵심
            │  무엇을 = 음악        │
            │  얼마나 = 관객        │
            └──────────┬──────────┘
                       │
            ┌──────────▼──────────┐
            │  DirectionParams    │
            │ 밀도·크기·속도·밝기   │
            │ 색상·확산·교란        │
            └──────────┬──────────┘
                       │
        ┌──────────────┼──────────────┐
        │              │              │
   Canvas 렌더링    WebSocket 송출   화면 리드아웃
   (5개 씬)        (외부 장비)       (수치 표시)
```

두 입력이 각각 다른 주기로 돕니다. 음악 분석은 오디오 스레드에서 버퍼 단위로, 관객 측정은 화면 갱신 주기로 돕니다. 연출 번역 엔진은 화면 갱신 시점에 두 값을 함께 읽습니다.

## 2. 사용자 흐름

### 2-1. 처음 여는 경우

```
페이지 접속
   ↓
빈 콘솔 (모든 값 0, 무대는 대기 화면)
   ↓
음원 파일을 끌어다 놓음  ──또는──  데모 신스 켜기
   ↓
파형이 그려지고 재생 버튼 활성화
   ↓
재생
   ↓
BPM 이 3~5초 안에 잡히고 비트가 뜀 · 직조 씬에 줄이 쌓이기 시작
```

관객 입력 없이도 여기까지 완결됩니다. 관객은 선택적 증폭기이지 전제 조건이 아닙니다.

### 2-2. 관객 입력을 붙이는 경우

```
04 패널에서 입력 방식 선택
   ↓
브라우저 권한 요청 → 허용
   ↓
보정 시작 (진행률 표시)
   ↓
약 20초 뒤 보정 완료
   ↓
관객이 움직이거나 소리를 냄
   ↓
관객 에너지 상승 → 연출 파라미터의 청록색 층이 두꺼워짐 → 화면이 강해짐
```

보정이 끝나기 전에도 동작은 합니다. 다만 값의 폭이 좁을 수 있어 화면에 진행률을 알립니다.

### 2-3. 리허설에서 조정하는 경우

```
곡 로드 → 조정할 구간에서 A·B 지점 지정 → 구간 반복
   ↓
08 패널에서 파라미터 확인
   ↓
관객 영향력 슬라이더로 개입 정도 조절
   ↓
씬 전환하며 어느 그림이 맞는지 확인
   ↓
프리셋 저장 (곡 이름과 함께)
```

### 2-4. 공연 당일

```
곡 로드 → 저장한 프리셋 자동 제안 → 적용
   ↓
출력 창을 열어 프로젝터 화면으로 이동 (O 키)
   ↓
외부 연동이 필요하면 WebSocket 연결
   ↓
공연 시작 → 재생
   ↓
(사고 시) B 키로 즉시 블랙아웃
```

## 3. 상태 전이

### 3-1. 오디오 소스 상태

```
none ──파일 로드──▶ file ──재생──▶ file(playing)
  │                                    │
  ├──마이크 허용──▶ mic (항상 재생 상태)  │
  │                                    │
  └──데모 켜기──▶ demo                  │
                                       │
     어느 상태에서든 다른 소스를 고르면 이전 소스를 정리하고 전환합니다
```

전환할 때 이전 소스 노드를 반드시 끊습니다. 끊지 않으면 소리가 겹치고 분석값이 오염됩니다.

### 3-2. 관객 입력 상태

```
off ──방식 선택──▶ requesting ──허용──▶ calibrating ──60초──▶ ready
                       │
                       └──거부──▶ error (사유 표시, 다른 방식 권유)
```

`calibrating` 에서도 값은 나옵니다. 다만 정규화 범위가 아직 좁습니다.

### 3-3. 음악 상태 판정

```
SILENT ──RMS 상승──▶ CALM ──비트 안정──▶ GROOVE
                                            │
                        ┌───────────────────┤
                        │                   │
                   에너지 상승          에너지 급락
                        │                   │
                        ▼                   ▼
                      BUILD ──정점──▶ PEAK   BREAK
                        │                   │
                        └───────────────────┘
                                 │
                               GROOVE 로 복귀
```

각 상태에는 최소 유지 시간 1.2초를 둡니다. 그보다 짧게 바뀌면 화면이 깜빡여 보입니다.

## 4. 두 개의 루프

**루프는 하나가 아니라 둘입니다.** 분석은 오디오 스레드의 시계를 따르고, 그리기는 각 창의 `requestAnimationFrame` 을 따릅니다. 나눈 이유는 `02-features.md` 의 `F-506-2` 에 있습니다. 콘솔 창이 가려지면 그 창의 rAF 가 멈추는데, 그때도 분석과 송출은 계속 돌아야 하기 때문입니다.

### 4-1. 분석 루프 — 오디오 스레드의 시계

```
1. 워크렛이 dt 와 함께 틱을 보냄 (창 상태와 무관)
2. 음악 분석값 읽기 (AnalyserNode.getByteFrequencyData)
3. 관객 에너지 읽기 (AudienceSource.read(dt))
4. 음악 상태 판정 (F-401)
5. 연출 파라미터 산출 (F-402) ← 두 신호가 합쳐지는 지점
6. 씬 입력을 한 곳에서 만들고 BroadcastChannel 로 송출 · WebSocket 송출 (초당 30회로 제한)
```

**틱 주기는 장치의 표본율에 따라 달라집니다.** 워크렛의 `process()` 는 128 표본마다 불리므로, 여섯 번에 한 번 보내면 48kHz 에서 62.5Hz, 44.1kHz 에서 약 57Hz 입니다. 정확한 값을 가정하지 말고 **워크렛이 실어 보낸 `dt` 를 쓰십시오.**

**시각의 기준은 `AudioContext.currentTime` 입니다.** rAF 가 멈추면 rAF 기준 시각도 멈추기 때문입니다.

**6번의 씬 입력을 한 곳에서 만드는 것이 중요합니다.** 중앙 무대와 출력 창이 각자 값을 모으면 한쪽만 고쳐졌을 때 두 화면이 갈립니다.

### 4-2. 그리기 루프 — 각 창의 rAF

```
7. 씬 렌더링 (콘솔 미리보기 · 출력 창이 각자)
8. 리드아웃 갱신 (매 프레임이 아니라 4프레임마다)
```

리드아웃을 매 프레임 하지 않는 이유는 DOM 갱신이 프레임 예산을 잡아먹기 때문입니다.

출력 창은 자기 rAF 로 그립니다. 콘솔이 가려져도 출력 창이 앞에 있으면 계속 그려집니다. 반대로 출력 창을 가리면 출력만 멈추고 콘솔은 계속 돕니다. 이건 정상입니다.

### 4-3. 값이 끊기면

출력 창이 0.5초 이상 새 값을 못 받으면 **마지막 값으로 계속 그립니다.** 화면에 오류 표시를 띄우지 않습니다. 관객이 보는 화면입니다.

### 4-4. 워크렛이 없을 때

워크렛 로드에 실패하거나 `AudioContext` 가 아직 없으면 **rAF 로 물러섭니다.** 창을 가리면 멈추지만 아무것도 안 도는 것보다 낫습니다.

`AudioContext` 는 사용자 조작 시점에 만들어지므로, 앱을 처음 열었을 때는 항상 이 상태입니다. 오디오가 켜지면 워크렛이 이어받고 rAF 구동은 끕니다. **둘이 동시에 돌면 분석이 두 번 실행됩니다.**

## 5. 오류 처리

| 상황 | 처리 |
|---|---|
| 오디오 컨텍스트가 정지 상태 | 사용자 조작 시점에 `resume()` 을 호출합니다. 브라우저 정책상 자동 시작이 막혀 있습니다 |
| 마이크 권한 거부 | 04 패널에 사유를 적고 시뮬레이션을 권합니다. 다른 기능은 계속 동작합니다 |
| 카메라 권한 거부 | 같은 방식으로 처리합니다 |
| 파일 디코딩 실패 | 형식을 안내하고 다른 파일을 권합니다 |
| WebSocket 연결 실패 | 원인을 구분해 안내합니다. HTTPS 페이지의 로컬 소켓 차단인지, 상대 쪽이 꺼져 있는지 |
| 프레임 속도 저하 | 30fps 아래로 5초 이상 지속되면 잔상과 입자 효과를 자동으로 낮추고 알립니다 |
| Supabase 연결 실패 | 프리셋을 브라우저 로컬에 임시 저장하고, 연결이 돌아오면 동기화를 시도합니다 |

공연 중에 쓰는 도구이므로 **어떤 오류도 화면을 멈추게 해서는 안 됩니다.** 한 부분이 실패하면 그 부분만 끄고 나머지는 계속 돌립니다.

## 6. 성능 예산

| 항목 | 목표 |
|---|---|
| 프레임 속도 | 60fps 유지, 최저 30fps |
| 오디오 분석 지연 | 50ms 이하 |
| 관객 측정 주기 | 30fps |
| 입력에서 화면까지 총 지연 | 120ms 이하 |

원 설계에서 딥러닝 음원 분리를 배제한 이유가 이 예산입니다. 200~700ms 가 드는 방식으로는 무대가 박자를 따라가지 못합니다.

측정 방법은 개발자 도구의 성능 탭이 아니라, 화면에 표시되는 fps 와 분석 주기를 기준으로 합니다. 리허설 환경에서 확인해야 의미가 있습니다.
